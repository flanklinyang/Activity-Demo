# 活动报名系统压测报告（第四轮：Redis 主从切换故障演练）

| 测试区域 | 本地开发环境（客户端与服务端同机）+ 三台虚拟机 Redis 高可用集群（192.168.100.200/201/202） |

## 2. 测试背景

前三轮报告覆盖了匀速 QPS、突发抢报场景，均基于**单实例 Redis**。本轮为 Redis 高可用改造后的首轮压测：

- 报名服务接入三台虚拟机上的 **1主2从 + 3哨兵** 集群（`redisclient/redis.go` 按 `redis.mode` 选择 `redis.NewFailoverClient`，主从切换时客户端自动跟随新主）
- 故障注入：报名阶段进行到一半时，在集群主节点上执行 `docker kill -s 9`（模拟主节点崩溃，非优雅停机）
- 验证目标：
  1. 切换窗口内请求行为——全部失败（fail closed）、无超卖
  2. 客户端自动恢复——服务零重启、零人工干预
  3. 切换后收敛——Redis 名额/报名集合 vs MySQL 记录完全一致

集群侧切换时长已在单独的集群实验中标定：判下线 5s（down-after-milliseconds）+ 选主切换 <1s，总计约 7.5s。本轮验证该窗口在**持续流量**下的系统表现。

## 3. 环境与工具改造

| 组件 | 改造 |
| --- | --- |
| 服务 Redis 客户端 | `redisclient/redis.go` 支持 `mode: sentinel`，经哨兵解析当前主；切换窗口内命令失败即报错（不重试绕过） |
| 配置 | `config.yaml` 切为哨兵模式：`master_name: mymaster`，哨兵地址 200/201/202:26379（密码经环境变量注入，不落报告） |
| 压测工具 | 一致性校验阶段新增 `-redis-sentinel`（哨兵地址列表）+ `-redis-master-name`，提供则走 FailoverClient——压测中途切换后仍能连上新主完成校验 |
| 集群 | 3 台 VM：200/201/202 各跑 redis(6379) + sentinel(26379)，`--network host`，quorum=2 |

## 4. 测试方法

- 流程：注册 → 登录拿 JWT → 创建活动（quota=6000）→ 匀速报名（100 QPS，60s）→ **中途杀主** → 等待落库 → 一致性校验
- 用户：`loadtest0000` ~ `loadtest5999`（历轮压测已存在），统一测试密码（见 loadtest 代码）
- 故障注入时机：报名阶段约进行到 1/6 处（约第 1000 个请求后），在集群主节点（201）执行 `docker kill -s 9 redis-slave`
- 观测手段：压测客户端统计（成功/业务失败/网络失败/延迟）、服务日志（客户端切换新主事件）、`/metrics`（HTTP 状态码与报名结果分布）、最终一致性校验
- 后端配置：`ratelimit.ip_per_sec = -1`（压测注册/登录单 IP 高并发，关闭 IP 限流）

## 6. 分析

### 6.1 拒绝窗口构成（约 9.1s）

913 个失败 ÷ 100 QPS ≈ **9.1s** 拒绝窗口，构成：

| 阶段 | 耗时 | 说明 |
| --- | ---: | --- |
| 判下线（down-after 5s + 探测间隔） | ~6s | 哨兵确认主节点死亡 |
| 选主切换 | <1s | 哨兵选举 + 新主晋升 |
| 客户端重新解析新主并恢复 | ~2s | FailoverClient 收到哨兵通知、重连新主 |

集群侧切换约 7.5s（与集群实验标定一致），客户端侧额外约 2s 收敛。

### 6.2 fail closed 分层：故障被限流中间件挡住

`signup_total{result="error"}` 为 0 是本轮最有价值的发现：**Redis 故障期间的请求没有一条进入报名 Lua**。链路中所有依赖 Redis 的中间件（用户限流）在 Redis 不可用时直接拒绝请求，故障被隔离在核心逻辑之外——这是"每层都 fail closed"设计的结果：

- 限流器失败关闭：Redis 不可用 → 500"限流服务异常"，不进入报名逻辑
- 报名 Lua 失败关闭：即使穿透到 Lua，Redis 错误也返回系统错误，不会出现"名额扣了但返回成功"的中间态
- 两层都拒绝而非放行，因此故障窗口内零脏数据、零超卖

### 6.3 数据一致性：未观察到尾部丢失

一致性校验四项全对。内网无分区场景下，主节点崩溃瞬间的已复制率极高（主写入后主动推送、毫秒级复制），"已成功报名但未复制到新主"的尾部丢失窗口未命中——与集群实验结论一致（内网竞态杀主两轮均未丢；丢尾需网络分区放大窗口）。

## 7. 结论

1. **切换窗口 ≈ 9.1s**：913 个失败请求（100 QPS 下），全部为业务失败（HTTP 500），网络失败为 0——拒绝窗口内系统稳定返回错误而非连接中断；
2. **故障隔离有效**：`signup_total{result="error"}=0`，失败全部发生在限流中间件，报名 Lua 零错误——Redis 故障被 fail closed 分层挡住，零超卖；
3. **客户端自动恢复**：FailoverClient 检测到切换后自动跟随新主（200），服务零重启、零人工干预，恢复后延迟回到 P50 3ms / P99 6.5ms；
4. **最终一致**：Redis 剩余名额、报名集合、MySQL 记录与去重数均与期望完全一致，无超卖、无重复、无遗漏；
5. **MQ 链路全程健康**：峰值队列深度 1，切换期间无消息积压，对账无需介入补发；
6. 报名链路在 Redis 主从切换下的可用性代价 = **失败请求数 ≈ 窗口时长 × QPS**（fail closed 拒绝），不产生正确性代价——这是本架构"可用性换一致性"设计的预期表现。

## 8. 限制与说明

- 本测试为**无网络分区的崩溃切换**：已复制的数据不丢，尾部丢失窗口（主已落盘未复制）极小且本轮未命中；分区场景下的丢尾已在集群实验（iptables 模拟）中单独验证
- 登录吞吐 142.2/s（bcrypt 瓶颈）与历轮一致，与故障演练结论无关
- 压测客户端与服务端同机，客户端侧资源竞争可能影响延迟绝对值，不影响故障行为结论
- 单活动 6000 名额场景下 Redis 集合操作规模小，大 key（报名集合数十万级）下的切换后增量同步性能未覆盖
- 失败窗口时长为实测推算（失败数 ÷ QPS），kill 精确时刻未与压测端时钟对齐，误差 ±1s
