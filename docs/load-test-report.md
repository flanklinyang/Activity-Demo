核心报名链路：

```text

  -> 消费者写入 MySQL 报名记录
  -> 更新活动 sign_up_count
```

## 4. QPS 口径

本报告中的 QPS 均为：

```text
QPS = 压测请求总数 / 压测耗时
```

需要注意：

- “总请求 QPS”包含成功和业务拒绝请求。
- “成功报名 QPS”只统计成功进入 RabbitMQ 的报名请求。
- 异步落库速度不等同于 HTTP 报名 QPS。
- 低于数秒的突发测试只能反映短时处理能力，不能直接代表持续 QPS。

## 6. 综合评价

### 6.1 已验证能力

- Redis Lua 能原子完成重复检查、名额扣减和用户登记。
- 100 个名额在 1000 次并发抢报中未超卖。
- RabbitMQ 正常时，异步报名记录可以最终全部落库。
- 活动报名人数最终与报名明细一致。
- JWT 鉴权、bcrypt 登录和用户注册功能正常。
- 1000 个用户的一次性成功报名链路正常。

### 6.2 性能判断

报名接口在本地短时压测中表现如下：

| 场景 | 总请求吞吐 |
| --- | ---: |
| 1000 个成功报名 | 约 6849 次/秒 |
| 1000 次抢 100 个名额 | 约 9361 次/秒 |

从短时突发结果看，报名接口具备处理 `1000 QPS` 的初步能力，但证据不足以确认能够稳定承受生产环境的 `1000 QPS`。

登录接口实测约为 `150 QPS`，注册接口约为 `112 QPS`。如果峰值流量包含大量登录或注册请求，当前结果不满足 `1000 QPS`。

### 6.3 当前结论

```text
功能正确性：通过
1000 用户一次性报名：通过
100 名额并发防超卖：通过
1000 QPS 短时报名能力：初步具备
1000 QPS 持续能力：未验证
1000 QPS 登录能力：不满足
生产环境稳定性：暂不能确认
```

## 7. 当前测试限制

- 报名压测持续时间只有 107 至 146 毫秒，属于瞬时突发。
- 压测客户端和后端运行在同一台电脑，可能争抢 CPU 和磁盘。
- 未经过 Nginx、TLS 或真实网络。
- 未采集服务器 CPU、内存、GC、MySQL 连接池、Redis 延迟和 RabbitMQ 队列深度。
- 未精确测量 RabbitMQ 消费延迟和消息最终清空时间。
- “名额不足”请求不进入 RabbitMQ 和 MySQL，不能代表全部成功时的数据库负载。
- 报告中的吞吐使用短时耗时外推，数值仅适合做初步判断。

## 8. 上线前风险

| 风险 | 影响 |
| --- | --- |
| 缺少活动与用户的联合唯一索引 | 并发或重复消费时数据库可能产生重复报名 |
| RabbitMQ 重试计数不会真实递增 | 消费失败可能无限重新入队 |
| Redis 扣名额和 MQ 发布不是原子操作 | 发布失败会导致名额被永久占用 |
| RabbitMQ 发布未使用 Confirm | 接口成功不代表消息已可靠保存 |
| 消费者单 goroutine 顺序处理 | 需要验证高 QPS 下的落库上限和队列积压 |
| Redis 数据丢失后无自动恢复 | 可能出现缓存与数据库不一致 |
| GORM `Info` 日志和 Gin debug 模式 | 持续压测时日志会明显影响性能 |
| 缺少系统指标和队列监控 | 无法及时发现性能瓶颈和消息积压 |

## 9. 下一轮 JMeter 压测方案

### 9.1 业务目标

假设用户规模为 3 万，峰值流量为 `1000 QPS`，建议先执行最接近真实容量上限的成功路径测试：

```text
用户数：30,000
活动名额：30,000
目标速率：1,000 QPS
持续时间：30 秒
总请求：30,000
预期成功：30,000
```

登录应在计时阶段之前完成，生成 30,000 个 JWT 并写入 CSV。正式压测只执行报名接口，避免 bcrypt 登录流量干扰报名结果。

### 9.2 JMeter 配置建议

```text
Threads：1000
Ramp-up：0 或 1 秒
Loop Count：30
CSV Variables：username,token
Authorization：Bearer ${token}
Throughput Shaping Timer：1000 RPS，持续 30 秒
```

运行命令：

```powershell
jmeter -n -t activity-signup.jmx -l signup-1000qps.jtl -e -o signup-1000qps-report
```

正式压测不要启用 `View Results Tree`。

### 9.3 容量余量测试

如果系统在 30,000 用户场景下表现稳定，再准备更多合成用户进行容量余量测试：

| 目标速率 | 持续时间 | 请求数量 | 预备用户数 |
| ---: | ---: | ---: | ---: |
| 500 QPS | 30 秒 | 15,000 | 15,000 |
| 1000 QPS | 30 秒 | 30,000 | 30,000 |
| 1500 QPS | 30 秒 | 45,000 | 45,000 |
| 2000 QPS | 30 秒 | 60,000 | 60,000 |

建议至少完成 `1500 QPS × 30 秒`，验证系统相对业务峰值有约 50% 的容量余量。

## 10. 最终判断

当前系统已经通过功能正确性和短时突发能力验证，但尚未通过面向 3 万用户的持续容量验收。

如果 `1000` 指报名峰值 QPS，现有短时结果说明系统有一定余量，但需要完成 `30,000` 用户、`1000 QPS`、`30` 秒的成功路径压测后才能给出稳定支撑结论。

如果 `1000` 中包含登录请求，当前登录吞吐约 `150 QPS`，系统不能承受 `1000 QPS` 登录流量。
