## 2. 本轮改造内容（压测前已完成）

上一轮报告（2026-09-17）遗留的风险，本轮全部处理：

| 改造项 | 说明 |
| --- | --- |
| Redis 持久化 | 开启 AOF `appendfsync always`（每次写 fsync 落盘后才响应）+ RDB，报名成功语义 = Redis 落盘即事实源 |
| MQ 生产者确认 | Publish 同步等待 broker 确认（超时 3s 可配），确认失败只告警，由对账兜底 |
| MQ 重试修复 | 重试次数放入消息体，失败重新发布而非 Nack requeue（修复原 header 计数不递增、会无限重试的 bug），超过 3 次进死信 |
| 数据库幂等 | `activity_sign_ups` 增加 `(activity_id, user_id)` 联合唯一索引，消费者"插入成功才计数"，唯一索引冲突视为幂等成功 |
| 已报名人数 | 不再落库 +1 统计，改为 Redis 报名集合 `SCARD` 实时获取 |
| 定时对账 | 每 60s 比对 Redis 报名集合与 MySQL 记录，差集补发 MQ 消息；业务队列有积压时跳过（避免把在途消息误判为丢失） |
| 死信出口 | 新增死信深度查询与重放函数，对账循环检测到死信积压会告警 |
| 登录鉴权 | 不变（JWT + bcrypt） |

**AOF 崩溃恢复验证（压测前）**：优雅停机重启 Redis 后，名额（quota=99）与报名集合完整恢复，报名链路正常，证明 AOF 恢复有效。

**环境注意**：Windows 版 Redis（5.0.14 fork）不支持 `aof-use-rdb-preamble` 配置项，已从配置中移除（该指令仅为重写优化，不影响数据安全）。

## 3. 压测方法与数据

压测程序流程：注册 3000 用户 → 登录获取 3000 个 JWT → 创建活动（quota=3000）→ 报名突发（300 并发）→ 等待队列排空与落库 → 一致性校验。

- 用户：`loadtest0000` ~ `loadtest2999`，密码 `123456`
- 报名活动：每轮新建（ID 3、4），quota=3000
- 后端运行模式：`GIN_MODE=release`（第 2 轮起）
- QPS 口径：请求总数 / 阶段耗时

## 4. 压测过程与问题解决

### 4.1 第一轮：压测客户端缺陷暴露

| 指标 | 结果 |
| --- | ---: |
| 注册 | 3000 成功，21.3s，140.7/s |
| 登录 | 3000 成功，19.0s，158.1/s |
| 报名成功 | 2091 |
| 报名网络失败 | **909（30%）** |
| 报名耗时 | 2.29s |

**问题**：30% 请求网络失败。后端日志 0 异常、0 panic，失败全部发生在客户端侧。

**诊断**：压测客户端使用 Go 默认 HTTP 连接池（每主机仅保留 2 个空闲连接），300 并发下几乎每个请求都新建 TCP 连接，短时间产生近万个 TIME_WAIT 套接字挤占动态端口池（16384 个），叠加 keep-alive 复用竞争，导致大量 `connection reset / refused`。

**解决**：客户端连接池调大（空闲连接 600，keep-alive 复用），并增加网络错误分类统计。**这是压测工具问题，不是服务端问题。**

### 4.2 第二轮：报名吞吐 902/s，撞上单通道确认串行化

| 指标 | 结果 |
| --- | ---: |
| 报名 | 3000/3000 成功，0 失败 |
| 吞吐 | 902/s |
| P50 / P90 / P95 / P99 | 327 / 373 / 378 / 442 ms |
| 最终一致性 | 通过（无超卖、无重复、无遗漏） |

**问题**：吞吐卡在 902/s，P50 延迟高达 327ms（300 并发下排队严重），存在明显的串行瓶颈。

**定位过程**：

1. 怀疑 `appendfsync always`：用 `redis-benchmark` 实测 SET/INCR 均达 **2.2 万/s**，排除；
2. 分析代码：所有发布共用一个 RabbitMQ channel 和一个互斥锁，每条消息必须等 broker 确认回包（局域网 RTT 约 1.1ms）才能发下一条，硬上限 ≈ 1000/s，与实测 902 吻合，**锁定为单通道发布确认串行化**。

**解决**：改造 `mq/rabbitmq.go`，增加 **16 通道发布池**——每个通道独立确认流、独立互斥锁，发布请求轮询分发，16 条消息可同时在飞。

### 4.3 第三轮：最终结果

| 指标 | 结果 |
| --- | ---: |
| 报名 | 3000/3000 成功，0 业务失败，0 网络失败 |
| 吞吐 | **3372/s** |
| P50 / P90 / P95 / P99 | 79 / 106 / 120 / 265 ms |
| 最大延迟 | 328 ms |
| 队列排空 | 0.9s |
| 全部落库 | 8.5s（消费者约 350 条/s） |

**最终一致性校验**：

| 数据项 | 结果 |
| --- | ---: |
| Redis 剩余名额 | 0（期望 0） |
| Redis 报名集合 | 3000（期望 3000） |
| MySQL 报名记录 | 3000 |
| MySQL 去重后记录 | 3000 |

结论：无超卖、无重复、无遗漏，最终一致。

### 4.4 第四轮：多消费者 + GORM 日志降级

| 指标 | 结果 |
| --- | ---: |
| 报名 | 3000/3000 成功，0 失败 |
| 吞吐 | 2223/s |
| P50 / P90 / P99 | 130 / 157 / 249 ms |
| 队列排空 | 1.4s |
| 全部落库 | **2.4s（消费者约 1250 条/s）** |

本轮改造：RabbitMQ 消费者从单 goroutine 改为 **5 个独立消费者**（`rabbitmq.consumer_count=5`，各自独占通道、Qos=20、独立 ACK、panic 恢复、通道断开自动重建），GORM 日志从 Info 降为 Warn。

消费者落库速度从约 350 条/s 提升到约 **1250 条/s**，超过 1000 QPS 报名流量，持续压测的积压风险解除。最终一致性校验全部通过。

## 7. 结论

1. **报名链路吞吐上限 ≥ 2223~3372/s（突发）**，超过 1000 QPS 目标 2~3 倍；
2. **正式容量验收通过**：30k 用户、1000 QPS × 30s，12 项验收指标全部达标，P95 7.7ms、P99 11ms、零失败零超卖；
3. **容量余量测试通过**：60k 用户、2000 QPS × 30s（业务峰值 2 倍），成功率 100%、P95 119.6ms、P99 231.8ms、零失败零超卖，报名结束后 17s 消化完积压；
4. `appendfsync always` 不是瓶颈（Redis 实测 2.2 万写/s），**发布确认串行化才是**，通道池化后已解决；
5. **消费者落库约 1250 条/s**（5 消费者 + GORM Warn），持续 1000 QPS 报名队列峰值深度仅 16，无积压风险；
6. 报名链路零失败、零超卖、零重复，最终一致性全部通过；
7. 第一轮的 30% 失败率为压测客户端问题，修复后未复现——**上一轮报告"短时 9k QPS"的结论也受到同样的客户端缺陷影响，参考价值存疑**。

## 8. 遗留问题

| 风险 | 说明 |
| --- | --- |
| 持续 2000 QPS 需扩容消费者 | 报名 2000 QPS > 消费者 1250/s，持续该流量会积压；需调大 `consumer_count` 或引入批量插入 |
| 死信重放未接 HTTP 接口 | `RequeueDeadLetters` 函数已实现，管理端入口待加 |
| 报名与登录吞吐差距大 | 登录约 160/s（bcrypt 瓶颈），报名 2000+ QPS，混合流量场景需注意 |
| 生产部署项未做 | Nginx/TLS、服务监控告警（Prometheus/Grafana）、GIN/GORM 生产配置 |

## 9. 下一步建议

1. 若目标峰值为 2000 QPS：扩容消费者（`consumer_count` 提升至 10 或引入批量插入）；
2. 死信重放补一个管理端入口；
3. 生产部署前补齐监控告警（MQ 队列深度、死信积压、Redis 延迟、MySQL 连接池）。
