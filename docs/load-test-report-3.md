## 1. 报告信息

| 项目 | 内容 |
| --- | --- |

| 测试区域 | 本地开发环境（客户端与服务端同机） |

| 测试目标 | 验证抢报场景（突发与匀速对比）下名额扣减的正确性（防超卖）与最终一致性 |

## 2. 测试背景

前两轮报告覆盖了**匀速 QPS** 场景（1000/2000 QPS 持续 30s，节奏器按目标速率分发请求）。本轮补充**突发流量**场景：所有请求不按节奏、全量同时发出，模拟抢报瞬间的流量尖峰（如秒杀开闸、活动上线瞬间）；并以同场景（10000 人抢 100 名额）的匀速 1000 QPS 压测作为对照组（5.3 节），量化两种流量形态的延迟差异。

突发场景与匀速场景的核心差异：

- 匀速场景考察**吞吐与延迟**；突发场景考察**瞬时过载下的正确性**——名额是否被超卖、拒绝是否准确、事后是否收敛一致
- 突发瞬时并发远超系统舒适区，延迟必然升高，关键指标是"全部请求多快消化完"与"0 超卖"

## 3. 压测工具改造

`loadtest/main.go` 新增两个参数（原有用法不受影响）：

| 参数 | 说明 |
| --- | --- |
| `-quota` | 活动名额，默认 = 用户数；支持名额远小于用户数的抢报场景 |
| `-burst` | 突发模式：跳过 QPS 节奏器，5000/10000 个请求一次性全部发出 |

一致性校验公式同步修正：`期望剩余名额 = 名额 - 成功数`（原公式假设名额=用户数，抢报场景下不成立）。

## 4. 测试方法

- 流程：注册 → 登录拿 JWT → 创建活动（quota=100）→ 突发报名 → 等待落库 → 一致性校验
- 用户：`loadtest0000` ~ `loadtest9999`（历轮压测已存在），密码 `123456`
- 报名并发：场景一/二为 300 worker 全量同时发出（`-burst`，无节奏控制）；场景三为 1000 QPS 节奏分发（不加 `-burst`）
- 后端配置：`ratelimit.ip_per_sec = -1`（压测注册/登录单 IP 高并发，关闭 IP 限流）
- QPS 口径：请求总数 / 阶段耗时

## 6. 对比分析

### 6.1 突发场景横向对比

| 指标 | 第一轮报告（1000 人抢 100） | 本轮 5000 人抢 100 | 本轮 10000 人抢 100 |
| --- | ---: | ---: | ---: |
| 竞争比 | 10:1 | 50:1 | 100:1 |
| 报名并发 worker | 100 | 300 | 300 |
| 总请求吞吐 | 9361/s | 7305/s | 9150/s |
| P50 | 9.6 ms | 60.5 ms | 154.8 ms |
| P99 | 25.3 ms | 120.7 ms | 213.6 ms |
| 全部消化耗时 | 107 ms | 0.68s | 1.09s |
| 超卖 | 0 | 0 | 0 |

规律：突发瞬时吞吐稳定在 **7.3k ~ 9.4k req/s** 区间（与第一轮短时突发 9361/s 一致）；延迟随并发规模上升——瞬时并发越大，Redis（单线程串行执行 Lua）与 Go 侧的排队越深，但全部请求均在 1.1s 内消化完毕，延迟仍低于 500ms 验收线。

### 6.2 突发 vs 匀速（同场景：10000 人抢 100 名额）

| 指标 | 突发（5.2 节） | 匀速 1000 QPS（5.3 节） |
| --- | ---: | ---: |
| 流量形态 | 10000 请求瞬间倾泻 | 1000 QPS 持续 10s |
| 总请求吞吐 | 9150/s | 1000/s |
| P50 | 154.8 ms | 7.0 ms |
| P95 | 197.5 ms | 13.1 ms |
| P99 | 213.6 ms | 17.3 ms |
| 全部请求消化 | 1.09s | 10s（按节奏） |
| 正确性 | 无超卖/无重复/无遗漏 | 无超卖/无重复/无遗漏 |

结论：突发的 213ms P99 是瞬时排队（Redis 单线程 Lua 串行）的物理结果，**不是持续容量上限**——同场景匀速 1000 QPS 下 P99 回落至 17.3ms，与第二轮正式验收（P99 11ms）一致。两种流量形态正确性均无破绽；持续容量以匀速压测为准（1000 QPS 舒适、2000 QPS 可扛），突发场景考验的是瞬时过载下的正确性与收敛速度。

### 6.3 落库表现

三个场景峰值队列深度均为 0：100 条报名消息低于 5 消费者 × 预取 20 的即时消费容量（100 条在飞上限），落库在报名结束后 1 秒内全部完成，无积压。

## 7. 结论

1. **防超卖经受住 100:1 竞争比考验**：10000 人同时抢 100 名额（突发与匀速两种形态），均恰好 100 人成功、9900 人被准确拒绝，Redis Lua 原子扣名额零超卖；
2. **突发吞吐稳定**：5000/10000 人两轮突发吞吐 7.3k/9.2k req/s，与第一轮 1000 人短时突发（9361/s）处于同一区间，短时处理能力约 9000 req/s；
3. **收敛迅速**：突发全部请求在 0.68s（5000 人）/ 1.09s（10000 人）内消化完毕，落库 1 秒内完成，无积压残留；
4. **突发延迟为瞬时排队而非容量上限**：同场景（10000 人抢 100 名额）匀速 1000 QPS 下 P99 仅 17.3ms（突发为 213.6ms），与第二轮正式验收（P99 11ms）一致，延迟随流量形态变化，系统持续能力不受突发延迟影响；
5. **最终一致全部通过**：三个场景下 Redis 剩余名额、报名集合、MySQL 记录与去重数均与期望完全一致；
6. 登录吞吐 135~149/s（bcrypt 瓶颈）与历轮一致，与抢报核心链路无关。

## 8. 限制与说明

- 突发延迟仅统计成功的 100 个请求样本，P99 与 Max 取到同一元素属统计口径现象；
- 压测客户端与服务端同机，客户端 300 worker 的调度能力可能先于服务端成为瓶颈，真实多机分布下瞬时并发会更高；
- 突发场景验证的是**短时尖峰**，持续容量结论仍以第二轮匀速压测（1000 QPS 舒适、2000 QPS 需扩容消费者）为准；
- 未采集服务端 CPU/GC/Redis 延迟明细，延迟归因（排队构成）基于架构推断。
